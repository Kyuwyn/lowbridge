# 03: Data model and content (Hundred Days / 筑基)

*Hundred Days* (筑基, "Foundation Establishment") is a Chinese cultivation idle game built as a **fork of Arcanum's engine**, not a game that merely resembles it. `src/dataLoader.js`, `src/modules/module.js`, `src/modules/parsing.js`, `src/items/base.js` and the save format are Arcanum's, lightly edited. The interesting question is therefore not "what does it share with Arcanum" but **what a different designer did with the same machine**: 4,520 records, 57 record types, 21 section tabs, a factory sim and a 500×300 tile map. Of the 184 field names in the data, 83 are Arcanum's, 101 are new, and 59 of Arcanum's were abandoned.

Numbers here are generated by `tools/census.py`; the raw tables live in [`data-census.md`](data-census.md). Regenerate both with:

```
python3 research/hundred-days-reference/tools/census.py /tmp/hundred-days-src
```

| Source | Used for |
|---|---|
| Translation fork `MaxRau/Hundred-days`, branch `english`, commit `9e1e0d3` (checked out at `/tmp/hundred-days-src`) | All counts, field frequencies, examples |
| Same checkout, branch `master` (upstream `Mostlai/Hundred-days`, HEAD `91ba763`) | The original Chinese for every example below |
| `js/hundred_days.js` (6.6 MB webpack bundle, `eval` payloads expanded by the fork's `tools/unminify.py`) | Engine semantics: what each field *does* |
| `js/*-ui.bundle.js` (lazy section chunks) | Which tab consumes which type |
| `tools/fixtures/save-all-unlocked.json` (a real all-sections save, 2,155 item entries) | §6, the save format |
| Arcanum testing data `/tmp/arcanum-data` (`unstable 0.12.12.9`) | Every "Arcanum vs fork" comparison |

The game reports itself as `P0.3.9c` (`src/gameState.js`). Companion pages: `01-shell-and-opening.md` for the screen, `04-engine-behind-the-curtain.md` for the engine diff and licensing, `05-community-wiki-notes.md` for the author's own wiki.

## 1. What loads, and how much of it

One manifest, `data/modules.json`, lists 56 core files and 16 modules. The loader (`dataLoader.loadGame`) fetches `./data/<name>.json` for each core entry, then `./data/modules/<name>.json` for each module, and merges modules into the core lists by type.

| Measure | Fork | Arcanum 0.12.12.9 |
|---|---:|---:|
| Core files listed | 56 | 32 |
| Records from core files | 3,345 | — |
| Modules listed | 16 | 50 |
| Records from modules | 1,175 | — |
| **Records loaded** | **4,520** | 3,407 |
| Distinct record types | 57 | 37 |
| Distinct field names | 184 | 142 |

(The sibling page `03-data-model.md` counts 3,389 for the same Arcanum build; the 18-record gap is the `hall` lists contributed by 17 modules plus one `resourcesUnused` record, which `census.py` counts and that page does not.)

Plus `hall.json` (19 records, 6 types), which `profile.js` loads as a *second, independent module* with its own localStorage file; items whose `module === 'hall'` are deliberately excluded from the character save.

The shape of the fork is visible in that table. It has **three times Arcanum's resources and 2.7× its furniture** but **60% of its upgrades and 40% of its classes**: progression moved out of the upgrade ladder and into `xiulian` (cultivation), `techo` (research) and the production chain, all of which are resource-and-facility systems rather than purchase systems. The monster count is inflated by one module: `elysium.json` alone contributes 600 of the 980.

### Empty files, and files that never load

`factclass_fu.json` is `[]` — it is listed in the manifest and instanced as the "production source" type (产品来源), so the slot exists but no content was ever written for it. `bio.json`, `elect.json` and `metal.json` are also `[]`, and are *not* in the manifest at all. All three names are live elsewhere: `bio` (Biology Lab) and `metal` (Smelting Furnace) are facility tags in `tags.json`, and `elect` (电能, Electrical Energy) is a resource. The empty files look like abandoned attempts to give each of those its own file.

And five module files are present but unlisted: `cthulhu.json` (13), `halloween.json` (69), `spring.json` (30), `Thought.json` (81), `familiars.json` (0, and the only file still using Arcanum's older `{name, data}` wrapper instead of `{module, data}`). `Thought.json` is the notable one: it contributes four `xiulian` records and 14 resources, so it is fork-authored content that was written and then switched off, not seasonal Arcanum content left behind.

There is also `data/modules/elysium` — a byte-identical copy of `elysium.json` **without the extension**. The loader fetches `<dir>/<name>.json`, so it is dead weight.

A type a module contributes that `initInstance()` does not recognise (`potions` from `winter`/`old_swamp`, `items` from `halloween`, `fupgrades` from `familiars`) is still parsed into the object index, then deleted at startup by `GameState.prepItems()` with a `missing hasTag(). Removing.` console warning. The fork ships two such orphan `potions` records in live modules.

## 2. The shared vocabulary

The Arcanum core survives essentially unchanged. `PrepData()` in `src/modules/parsing.js` still decides what a field means purely by its **name**, and that function is the real schema:

- `mod`, `runmod`, `alter` → `ParseMods` (standing modifiers, dotted paths into other records)
- `effect`, `result`, `xiulianresult`, `ele`, `damage_element` → `ParseEffects(MakeEffectFunc)`
- `cost`, `buy`, `acost`, `counterattack`, `scost`, `startcost`, `lhxy` → `ParseEffects(MakeCostFunc)`
- `require`, `need`, `equneed`, `show_require` → `ParseRequire`

Everything else is coerced by value shape (percent, range, per-mod, at-mod) and otherwise stored raw. **The fork extended the schema by adding names to those four lists** — five new cost-like fields (`acost`, `counterattack`, `scost`, `startcost`, `lhxy`), three new effect-like fields (`xiulianresult`, `ele`, `damage_element`) and two new requirement fields (`equneed`, `show_require`) — rather than by changing the engine. The other 91 new field names are read directly by one system each.

In the fork, nearly every new type is instanced as a `Resource` with `val`/`max`, so `max` is the primary "how many of these can exist" statement for cultivation nodes, conquests, commands, true souls, products and factories alike.

## 3. The new content types

Thirty-one of the 57 types have no Arcanum counterpart. Each belongs to a tab or a panel.

### 3.1 `xiulian` — cultivation (193 records, tab **Cultivation** / 修炼)

The spine of the game, and the clearest statement of what the fork is for. Each record is one **node on a research-like cultivation lattice**: a repeatable purchase with `max` levels, a `cost` paid per level, and an `xiulianresult` effect map paid out per level. Fields are uniform across all 193: `id`, `name`, `desc`, `tags`, `require`, `max`, `cost`, `xiulianresult` on every record; `buy` on 7 and `flavor` on 1.

`tags` is a single group name, and the 193 nodes fall into exactly **17 groups**:

| Group (EN) | Group (ZH) | n | Group (EN) | Group (ZH) | n |
|---|---|---:|---|---|---:|
| Life Construction | 生命构造 | 31 | Energy Physics | 能量物理 | 8 |
| Energy Deconstruction | 能量解构 | 19 | Geometry | 几何 | 7 |
| Elemental Engineering | 元素工程 | 19 | Celestial Ladder | 通天阶梯 | 6 |
| Path | 路径 | 16 | Phase Transition | 形态变化 | 6 |
| Hope of Immortality | 永生之望 | 16 | Death | 死亡 | 6 |
| Cognition | 思维 | 14 | Multivariate Calculus | 多元程式 | 6 |
| Art of Observation | 观测之术 | 12 | Sea of Information | 信息海 | 5 |
| Material Structure | 物体结构 | 11 | Spatial Systems | 空间系 | 3 |
| Foothold | 立足 | 8 | | | |

The tab unlocks on `g.heli` — bare truthiness of Coherence (合理), the resource the whole cultivation economy runs on.

```jsonc
// data/xiulian.json[0]  —  english branch
{
  "id": "heli_li_1",
  "name": "Coherence Fundamentals (Path)",
  "desc": "For this new power, we must learn to utilize it with maximum efficiency.",
  "tags": "Path",
  "require": "g.heli",
  "max": 2,
  "buy":  { "books": 1 },
  "cost": { "ganwu": 1, "heli": 3, "books": 1, "exe_paper": 2 },
  "xiulianresult": { "time": 13, "heli.rate": 0.01, "xiulian_heli_1": 1 }
}
```

```jsonc
// master branch
{ "id": "heli_li_1", "name": "初步认识合理之理(路径)", "tags": "路径",
  "desc": "对于这种新的力量,我们应该学会如何以最大效率的利用他", ... }
```

Note `"time": 13` in the payout: cultivation *costs lifespan*. And `"xiulian_heli_1": 1` sets a flag resource that other content gates on — the lattice talks to itself through resources, not through `lock`/`enable`.

The `Xiulian` class extends `GData` with `{repeat: true, stack: true}` and saves `complete` alongside the usual delta.

### 3.2 `techo` — research tree (30 records, tab **Research** / `sect_techo`)

Three domains, run as three parallel slots on the player:

| Domain tag | Records | Point resource |
|---|---:|---|
| `physics-domain` / 物理域 | 13 | `physic_point` / `physic_rate` |
| `engineering-domain` / 工程域 | 11 | `engineer_point` / `engineer_rate` |
| `social-domain` / 社会域 | 6 | `socia_point` / `socia_rate` |

`player_res.json`'s single record `player_techo_stata` holds `physic`, `social`, `engineer` — each either `"none"` or the id of the node currently being researched. `doReserach()` ticks the chosen node's `research_now_point` toward its `research_need_point` (1 to 20,000 across the tree) while paying its `run` drain, then `amount(1)`s it and clears the slot. `doTecho()` applies the `mod` of every completed node every frame. So research is a *three-lane job queue over a flat list*, not a graph: the "tree" is entirely in the `require` strings.

```jsonc
// data/techo.json[0]
{ "id": "techo_soc_sls", "name": "Life Spirit Stone Collection",   // 生灵石收敛
  "tags": "social-domain",                                          // 社会域
  "desc": "Automatically obtains Life Spirit Stones.",              // 自动获取生灵石
  "require": "g.xl_lj_konwledege_1>=1",
  "research_need_point": 1000,
  "run": { "money": 100, "ganwu": 50 },
  "mod": { "shenglingshi.max": 20, "shenglingshi.rate": 0.1 },
  "max": 1 }
```

### 3.3 `conquer` — conquest (22 records, tab **Conquest**, `g.shenshi_3>=3`)

Settlements you take by force, and the only purchase-shaped action **resolved by a dice roll**. `buy` reveals/claims the target; `acost` is the attack bill; `gattack()` rolls `Math.random()*100 <= cgl*100`; on success you get `result` and `mod`, on failure you pay `counterattack` instead. `cgl` compares the player's combat effectiveness `zdxn` — a formula over `f_power`, `zhuzhidu` (cohesion), `alculation` (processing power) and `yanzhandu` (war weariness) — against the target's `power`, and returns a flat 100% once `zdxn >= 6 × power`.

```jsonc
// data/conquer.json[0]
{ "id": "conquer_small",
  "name": "Small Town [Press E to open indicator]",     // 小城镇【按E打开指示器】
  "tags": "Tier 1",                                      // 1级
  "desc": "A sparsely populated town with weak defenses but a small footprint.",
  "power": 30, "max": 1, "val": 0,
  "require": "g.human_power>=4",
  "buy": { "money": 100 },
  "counterattack": { "shiqi": 11, "zhuzhidu": 11, "money": 150, "conquer_small": 1 },
  "acost": { "money": 150, "qingjia": 40, "zhongjia": 30, "human_power": 40, "alculation": 10 },
  "mod": { "f_power": 5, "space.max": 5, "alculation.max": 10,
           "alculation.rate": 0.2, "human_power.max": 20 },
  "result": { "super_mind": 1, "yanzhandu": 20 } }
```

Taking the town raises your land `space.max` and your processing-power caps; failing costs morale (`shiqi`), cohesion (`zhuzhidu`) and the 150 coins. Note that the successful `result` *also* adds 20 war weariness, so each conquest feeds back into the formula that decides the next one.

The Conquest tab also hosts two sub-panels: `adv_weapon` (5 records, 杀伤武器 "ordnance" — the armour and munitions stock consumed by `acost`, each with a `damage_element` payout and a `fill` target) and `weapon_factory` (7 records, 武器工厂 — furniture-like buildings whose `mod` raises an ordnance item's `max` and `rate`). The five `fight` records (伤害要素 "damage factors": Light / Medium / Heavy Armour, Corrupt, Frozen) are the stock categories those feed.

### 3.4 `humanr` — workforce directives (19 records, tab **Workforce** / 人力, `g.rlgl>=1`)

Standing orders that convert workforce into output. Perfectly uniform: all 19 carry exactly `id`, `name`, `desc`, `require`, `max`, `need`, `startcost`, `mod` — **no `cost`, no `result`, no `effect`**. A directive is pure economics: pay `startcost` once, then hold a permanent `mod` that trades caps and rates against each other. Seventeen are `…zhiling`/`…zl` commands (Money, Manual Power, Thermal Power, Zero Crystal, Draft Paper, Experience Log, Star Map, FC Alloy, Neural Material, Titanium Plate, Culture Medium, Culture Solution, Tier-1 Bio Sample, Pure White Material, Sub-Polar Cable, High-Temperature Flow, Frozen Core); two are workshops.

`gaddzl()` refuses unless `command_code.val + it.mod.command_code <= command_code.max` — `command_code` (指令容量, base max 3) is the directive slot budget, so the whole system is a slot-allocation puzzle expressed entirely in `mod`.

```jsonc
// data/humanr.json[0]
{ "id": "yjjqzl", "name": "Money Command",                 // 金钱指令
  "desc": "Deploy workforce to gather funds.",              // 派遣人力获取钱财
  "require": "g.xiulian_xxh_mtcb>=1", "max": 5,
  "need": "g.human_power>=200",
  "startcost": { "alculation": 500, "human_power": 200, "money": 80,
                 "heli": 30, "chaos": 30, "elect": 30, "shenshi": 5 },
  "mod": { "command_code": 1, "space.max": -20, "human_power.max": -200,
           "alculation.max": -150, "alculation.rate": -1,
           "human_power.rate": -0.4, "money.rate": 1.5 } }
```

### 3.6 True soul: `realsoul`, `realsoul_fu`, `soulpice` (19 + 19 + 19, popup from the **Character** tab)

A three-file idiom that is worth studying, because it is the fork's answer to Arcanum's `X.mod.Y` education ladder *without* authoring 100 upgrade records.

- `realsoul` (真魂) — the visible soul. `lhxy` is its synthesis cost, `scost` its upgrade cost, `craft_result` grants one `*_fu`, `up_mod` is the display of what each upgrade buys, `mod` is its current standing bonus, `img` its icon.
- `realsoul_fu` (真魂, hidden) — the invisible counter. One per soul, `max: 1e12`, `require: "g.hp>=1"` (always true), and a `mod` that **patches the parent soul's own tables**.
- `soulpice` (真魂碎片) — 19 drop materials, uniform at `{id, name, desc, val, max, locked, flavor}`. Exactly one of them, `blood_soulcore_pice`, carries `more_info` naming the dungeon it drops from; the other eighteen leave the player to guess.

  "scost": { "exp": 500, "element_blood": 20, "zhenhun_pice_1": 40, "blood_soulcore_pice": 5 },
  "craft_result": { "blood_jihun_fu": 1 },
  "up_mod": { "blood_jihun.mod.max_rs": 1, "blood_jihun.mod.hp.max": 20 },

### 3.8 `scena` — branching dialogue (1 record)

One record, `scena_1` (分配属性, "Attribute Allocation"), whose entire content is a `branches` array. ## 4. The expression language

`ParseRequire` is unchanged: a string matching `/^[A-Za-z_]+\w*$/` stays a bare id (looked up as an item or TagSet), anything else becomes `new Function("g","i","s", "return " + text)`. Costs use `new Function('g,a', …)`, effects `new Function('g,t,a', …)`.

**All of Arcanum's operators survive, and the fork uses almost none of them.** Over 2,674 expression strings:

| Construct | Fork | Arcanum | Verdict |
|---|---:|---:|---|
| `g.<id>` | 2,562 | 2,383 | survives, universal |
| `>=` / `>` | 2,315 / 2,548 | 1,312 / 2,183 | survives |
| `&&` | 555 | 986 | survives |
| `\|\|` | **10** | 106 | survives, nearly abandoned |
| `==` | 9 | 130 | survives, nearly abandoned |
| `(…)` grouping, `+` | 23 / 19 | 228 / 93 | survives, nearly abandoned |
| `!`, `-`, `*` | 0 | 12 / 26 / 23 | unused |
| `.max` / `.rate` / `.value` dotted mods | 10 / 5 / 13 | 203 / 1 / 4 | survives, much rarer |
| `.level` | 14 | 2 | **newly common** (`g.player.level>=39`, `g.level>=40`) |
| `.owned`, `.locked`, `.getWeapon`, `.hasDot` | 0 | 55 / 25 / 42 / 6 | unused |
| `.hasType('skill')` | 2 | 1 | survives (`g.runner.hasType('skill')` on two tasks) |
| `g.t_<tag>` tag counters | 0 | 408 | **renamed, not removed** — see below |
| tag counters under any spelling | 258 | 408 | survives |
| bare id | 111 | 576 | survives |
| `Math.*` in costs | 0 | 23 | unused |
| Expression-valued costs | 1 | 38 | effectively abandoned |

Only **77 of 2,674 expressions (2.9%)** use anything beyond `g.<id> <cmp> <number>` chained with `&&`, and reading them shows almost all are inherited Arcanum content (spells, classes, the `puppeteer`/`ritualist`/`winter` modules). The fork's own content — `xiulian`, `techo`, `conquer`, `humanr`, `factclass` — is written entirely in the simplest subset. [INFERENCE] This looks less like a design decision than like a second author who learned the subset that worked and never explored the rest.

### Idioms the fork added

**`g.hp>=1` as "always true".** Used 23 times (19 of the 19 `realsoul_fu` records, 3 missions, and the `sect_achievement` section). The player starts with `hp: 5`, so this is a no-op gate written where Arcanum would omit `require` entirely. Worth recognising: it is a tell that the author wanted the field present for uniformity.

**Tag counters, renamed.** The `g.t_<tag>` count of zero is the most misleading number in the table, so it is worth being precise: the **mechanism is untouched and heavily used; only the naming convention changed.**

`TagSet.valueOf()` sums the values of every owned item carrying the tag, so `g.<tag> >= 1` counts records exactly as Arcanum's `g.t_<tag> >= 1` does. Arcanum named its tags `t_shapeshiftclass`, `t_rest`, `t_runes` and queried them with the prefix visible. The fork names its tags plainly — `TENV`, `artifice_1`, `green_lab`, `hotlab` — and queries them as `g.artifice_1>=1` or, when truthiness is enough, as the bare id `"TENTYV"`. Counting both spellings, the fork has **258 tag gates** (197 compared to a number, 61 bare) against Arcanum's 408.

What *did* change is what tags are for. All 64 of the fork's 66 tags that carry the new `t_furniture: true` flag name a **facility**: `TENV` (10V Power Supply), `work_space` (Workbench), `hotlab` (High-Temperature Laboratory), `artifice_1` (Basic Refining Bench), `green_lab` (Green Laboratory), `dexterous` (Ingenious Mechanism)… `TagSet`'s constructor appends `"(Facility Support)"` to the display name when the flag is set, so the tooltip reads correctly with no extra authoring. The busiest are `green_lab` (26 gates), `TENTYV` (23), `artifice_1` (22), `mix_1` (12).

So where Arcanum asked "how many shapeshifter classes do you have", the fork asks "do you have a 20V supply and a refining bench". Same counter, different question — and it is what makes `equneed` work: nearly every `equneed` in the data is `g.<facility-tag>>=1`.

Four `t_`-prefixed tags do survive as *values* inherited from Arcanum modules (`t_ritual` on 23 records, `t_tier0` on 14, `t_runes` on 10, `t_rest` on 8), but nothing in the fork's data queries them.

**`spellcraft`** is the one surviving Arcanum-style bare-id section gate (`sect_scraft`) — and it is broken; see below. **`g.t_tier0`** is never written: `t_tier0` exists as a `tags` value on 14 class records, but nothing queries it — the tier system is gated on plain resources (`g.tier2>0`) inherited from Arcanum.

### 191 records are gated on ids that no longer exist

This is the most consequential thing the census turned up, so it is worth stating carefully.

`unlockTest()` resolves a bare-id gate with `getData(test)` and returns falsy when the id is unknown. An expression reading `g.<unknown>` gets `undefined`, so every comparison against it is false. Either way, **a record whose `require` names something nothing defines can never unlock.**

The fork deleted Arcanum's elemental lore skills, its class graph and its `spellbook`/`enchanting`/`evil` stats, but kept a great deal of the content gated on them. Counting ids the engine creates itself (`player`, `runner`, `inv`, `minions`, `spelllist`, …) as declared, **191 of 4,520 loaded records (4%) have a dangling gate**:

| Type | Dangling | Of | Share |
|---|---:|---:|---:|
| spells | 125 | 244 | **51%** |
| enchants | 21 | 30 | **70%** |
| tasks | 11 | 335 | 3% |
| resources | 10 | 339 | 3% |
| skills / upgrades | 5 / 5 | 99 / 379 | 5% / 1% |
| dungeons / furniture | 3 / 3 | 56 / 351 | 5% / 1% |
| sections | 2 | 21 | 10% |
| potions, factrecipe, homes, locales, monsters | 1–2 each | | |

The most-named missing ids are `enchanting` (19 gates), `lightlore` (17), `airlore` (15), `waterlore` (15), `earthlore` (14), `evil` (14), `firelore` (13), `lore` (13), `spellbook` (13), `naturelore` (12). Half the spell list is therefore decoration: the fork's real magic is `xiulian` and `element`, and the Arcanum spellbook was never cleaned out.

Two of the 21 section tabs are among the casualties. `sect_scraft` requires the bare id `spellcraft`, and `sect_bestiary` requires `g.bestiary>0||g.lore>=11` — none of `spellcraft`, `bestiary` or `lore` is defined anywhere in the data, so neither tab can open, even though `scraft-ui.bundle.js` (55 KB) and `bestiary-ui.bundle.js` (28 KB) both ship.

The failure mode is specific to bare-id gates that may mean "record" *or* "tag": `unlockTest` cannot tell the difference, so deleting either silently breaks every gate that named it, with no load-time error. One record in the inherited `winter` module carries `"need": "potsource"`, which was a tag in Arcanum's 243-tag `tags.json` and is not among the fork's 66; the gate is now permanently false. It survived the cut only by luck that `workspace`, in the same position in `puppeteer` and `ritualist`, happens to be a tag the fork still uses.

The one *intentional* dangling gate is `template_burn`'s `require: "g.template_item>=1"` — `template_item` is the placeholder the loader substitutes when it clones the template into a real combustion recipe (§3.5).

Full per-record detail is in [`data-census.md` §14](data-census.md).

### Value grammar

| Shape | Regex / form | Fork uses | Arcanum uses |
|---|---|---:|---:|
| Range | `"2~7"` | 483 | 763 |
| Percent | `"20%"`, `"0.01+5%"` | 201 | 509 |
| Per-mod | `"<value>:<per>"` — "value per N held" | 9 | 4 |

Patching another record's table is still the compounding engine, and the fork does one thing Arcanum did not: **it patches `cost` tables**. `blood_jihun_fu.mod` contains `"blood_jihun.scost.blood_soulcore_pice": 0.3`, making each true-soul upgrade raise the price of the next. Arcanum only ever patched `mod`, `result` and `effect`.

## 6. Save and load

### It is still Arcanum's delta save

`GameState.toJSON()` writes:

```jsonc
{
  "version": "P0.3.9c",
  "pid":     "p…",          // TimeId-generated player id
  "name":    "<player name>",
  "items":   { /* every item, delta-encoded */ },
  "bars":    { /* quickbars */ },
  "slots":   { "<slot>": "<item id>" },
  "equip":   { /* worn equipment */ },
  "combat":  { /* live fight */ },
  "drops":   { /* loot not yet taken */ },
  "explore": { },
  "sellRate": 0.5,
  "NEXT_ID": 0
}
```

Against Arcanum's keys this **adds** `equip` as a top level and **drops** `lastUpdate`, `siege` (no siege minigame) and `currentSpellLoadout`.

### Measured against a real save

`tools/fixtures/save-all-unlocked.json` in the translation repo is a genuine late-game save (character 小虾米, every section unlocked). Loading it settles the question:

| Measure | Value |
|---|---:|
| Save payload | 152,664 bytes |
| Content JSON it describes | 2,273,018 bytes |
| Item entries | 2,155 |
| Entries with exactly one field | 1,535 |
| Entries carrying `desc`, `require`, `mod` or `tags` | **0** |

A `xiulian` node the player has not touched is stored as `{"repeat": true, "id": "heli_li_1"}` against a template of `{id, name, desc, tags, require, max, cost, xiulianresult}`. **It is a sparse delta**, exactly like Arcanum's: 7% of the content size, carrying only what the player changed.

### Two thirds of the save is one wasted key

1,485 of the 2,155 entries are *literally* `{"repeat": true}`, and 2,095 of 2,155 carry that key. It is not player state. Several item constructors run `if ( this.repeat !== false ) this.repeat = true;`, and seven item classes (`market`, `player_res`, `potion`, `race`, `skill_extend`, `techo`, `xiulian`) declare `repeat: true` as a class default. None of that reaches the **frozen template** that `changes()` diffs against, so the diff cannot cancel it and every record writes it out forever.

The lesson generalises past this bug: `changes(instance, template)` only strips what the template *also* says. A default applied in a constructor instead of in the data is invisible to the diff and becomes permanent save weight. The fix is to put defaults in the template, which is exactly what Lowbridge does by recomputing derived fields from content rather than seeding them on the instance.

### The delta mechanism

Unchanged from Arcanum, in `src/items/base.js`:

```js
toJSON() {
  if ( this.save && (this.value>0||this.owned) ) return this.forceSave();
  let vars = jsonify(this, JSONIgnore);
  if ( this.template ) vars = changes( vars, this.template );   // <- the delta
  if ( this.locked === false && this.template && this.template.locked !== false ) vars.locked = this.locked;
  …
}
```

`JSONIgnore` lists the fields never written (`template`, `id`, `type`, `module`, `name`, `desc`, `tags`, `mod`, `require`, `need`, `equneed`, `effect`, `length`, `value`, `locked`, `inp`, `outp`, `power`, …), and `changes()` strips anything equal to the frozen template. Everything derivable — caps, rates, applied mods — is recomputed on load from data plus owned records. So, as in Arcanum, the save is mostly a visibility-and-progress bitmap keyed by stable ids, and content can be added without migrating saves.

Where it is stored *is* different: Arcanum's IndexedDB path (`src/modules/persist/persist-db.js`) is absent from every fork bundle, so Hundred Days is localStorage-only.

Six item classes override `toJSON` to force-save fields the delta would otherwise drop — and all six also re-write `id`, which `JSONIgnore` strips precisely because it is redundant:

| Class | Force-saves |
|---|---|
| `Techo` | `recipe`, `research_now_point`, `research_need_point` |
| `Xiulian` | `recipe`, `complete` |
| `Factrecipe` | `inpval`, `outpval` (the live port configuration), `working` |
| `PlayerRes` | `physic`, `social`, `engineer`, `logversion`, `frecipever` |
| `SkillExtend` | `isCategory`, and for roots `factor` and `spendtotal` |
| `Race` | `damge_bonus` *(sic)* |

`Attack.toJSON()` goes the other way and returns `{}`; its entire body is commented out, so live attacks are not persisted.

`GameState.saveItems` holds *every* item, not a filtered set; `addItem()` is the one place that excludes anything, and it excludes `module === 'hall'`. The Hall is persisted separately under localStorage key `hall`.

### There is no save versioning

`version: "P0.3.9c"` is written and **never read**. There is no migration table, no version check on load, and no refusal of old saves. `mergeItems()` merges whatever is in the save over the current template, so an outdated save silently inherits new fields and keeps stale ones. The only compatibility code is an `alias` lookup (`raws[p].alias`) that renames three records in the manifest data (two spells, one upgrade) plus one in `hall.json`, and a legacy `player.hid` → `pid` fallback.

### `logversion` and `frecipever` are changelog markers, not save versions

This is worth stating plainly because the names mislead. `data/player.json` contains a hidden stat record:

```jsonc
{ "id": "logversion", "name": "20230010", "logversion": "2023011",
  "frecipever": "20403r01", "hide": true, "locked": false, "stat": true, "val": 0 }
```

and `data/player_res.json` contains the single mutable record:

```jsonc
{ "id": "player_techo_stata", "physic": "none", "social": "none",
  "engineer": "none", "logversion": "", "frecipever": "" }
```

`vitals.vue` compares the two. When `player_techo_stata.logversion !== logversion.logversion`, a "what's new" banner shows; dismissing it (`closetips()`) copies the string across. `frecipever` does the same for "the production recipes changed". They are **acknowledgement flags for in-game notices**, shipped in content so the author can bump them without touching code.

### Persistence targets

| Layer | File | Mechanism |
|---|---|---|
| Local character | `localStorage["chars/<pid>"]` | `persistLocal.js` — `window.localStorage`, not IndexedDB |
| Local hall | `localStorage["hall"]` | same |
| Settings | `localStorage["settings//<charid>/"]` | same |
| Remote character | `usersaves/<uid>/<pid>.json` | Firebase Storage `putString(save, RAW)` |
| Remote hall | `usersaves/<uid>/hall.json` | same |

Autosave is `setInterval(… , 1000 * SAVE_TIME)` with `SAVE_TIME = 30`, and the autosave setting is read but then ignored (`//if ( setting && !this.saver )` is commented out in favour of `if (!this.saver)`), so it always runs.

Cloud save is lazy-loaded: `persist.js` fires `import('./persistRemote')` at module scope, which pulls `remote.bundle.js` (35 KB) + `vendors~remote.bundle.js` (419 KB, nearly all of it the Firebase SDK). `index.html` separately loads `firebase-ui-auth.js` and its CSS from `gstatic.com`. `Persist.remoteFirst` defaults to `false`, so local wins unless the player asks otherwise; a remote load is attempted only if local returns nothing *and* the user is logged in.

The Firebase config in `remote.bundle.js` is **Arcanum's**: project `theory-of-magic-49589`, `theory-of-magic-49589.firebaseapp.com`, with the web API key and app id inlined. The fork never re-pointed it. `login()` and `register()` are empty stubs; auth comes entirely from the FirebaseUI widget.

## 7. What this means for Lowbridge

Lowbridge is a clean implementation inspired by Arcanum (`AGENTS.md`), and the fork is a second data point on the *same* engine: evidence about what the vocabulary affords when a different designer pushes on it. Nothing here is binding; `design/DESIGN-PLAN-2026-10-18.md` and the ADRs win.

**Confirmations.** Six things the fork independently validates about Lowbridge's existing choices:

1. **One vocabulary, many types.** The fork added thirty-one content types without changing the engine, purely by adding field *names* to four lists in `PrepData()`. Lowbridge's `recordFields` set in `scripts/validate.ts` is the same discipline with a gate attached. Keep the gate: the fork's unvalidated vocabulary is how it ended up with `isbuild` on 16 tiles that nothing reads, a `cultivation` group next to `Cultivation`, and a `factclass_fu` type wired into the loader with zero records.
2. **`X.mod.Y` patching is the compounding engine.** Both games reach for it. The fork's extension — patching a *cost* table so each purchase raises the next price (`blood_jihun_fu` → `blood_jihun.scost.*`) — is a genuinely useful idea Lowbridge's `X.mod.Y` already supports mechanically (`src/engine.ts:235-246`) and could use for escalating prices without authoring a curve.
3. **Delta saves keyed by stable ids.** The fork kept Arcanum's `changes(vars, template)` and never needed a migration: a real late-game save is 149 KB describing 2.2 MB of content. Lowbridge's sparse delta (`src/persistence.ts`) is the same bet. Two differences favour Lowbridge: it *refuses* old versions by name (`src/persistence.ts:155-160`) where the fork writes a version string and never reads it; and it recomputes derived fields rather than seeding them on the instance, which is what lets its diff actually cancel — 69% of the fork's save entries are a `repeat: true` set in a constructor that the template cannot diff away.
4. **Derived fields must be recomputed, never saved.** The fork's `JSONIgnore` and Lowbridge's `DERIVED_FIELDS` are the same list by a different name.
5. **Resources that carry `mod` make inventory a build decision.** The fork leans on this harder than Arcanum (339 resources, most of them modifier-bearing).
6. **Tag counters earn their keep.** Both forks of the idea use them heavily — 258 tag gates here, 408 in Arcanum — which is a reasonable sign that Lowbridge's `g.t_<tag>` will matter more as content grows, even though it is only four expressions today. The fork also shows a use Lowbridge has not needed yet: `t_furniture: true` on a tag record marks it as a *facility*, and `TagSet` auto-suffixes "(Facility Support)" to the display name, so "needs a workbench" is authored once on the tag rather than in every tooltip.

**Warnings.** Six things the fork shows going wrong, in descending order of how much they justify work Lowbridge has already done:

1. **Reachability must be checked, or content silently dies.** 191 of 4,520 records — including 51% of the spell list, 70% of the enchants and 5 of the 21 section tabs — are gated on ids that no record defines, because the fork deleted Arcanum's lore skills, class graph and most of its tags without auditing what referenced them. Nothing warns at load; the records simply never appear. This is precisely what `scripts/validate.ts`'s reachability pass buys, and it is the single strongest argument for keeping `bun run validate` in the gate: Lowbridge proves 109/109 records reachable by playing the real engine, and the fork is what the alternative looks like.
2. **Bare-id gates that can mean "record" *or* "tag" are a trap.** `unlockTest` cannot distinguish them, so deleting either breaks every gate that named it with no error. Lowbridge already rejects a record id equal to a tag (`scripts/validate.ts:120`) and keeps `g.t_<tag>` syntactically distinct from `g.<id>`; both choices avoid this directly.
3. **Unvalidated content rots quietly in other ways too.** Eleven unloaded files, five unlisted modules, a byte-identical extensionless copy of a 314 KB module, a declared type with zero records, a dead field on 16 tiles, orphan `potions` records deleted at every startup with a console warning, and a resource `group` of `cultivation` sitting next to 165 in `Cultivation`. Lowbridge's "any JSON field outside the vocabulary fails validation" rule prevents most of this class.
4. **A rich expression language goes unused if the content author does not need it.** 97% of the fork's 2,674 expressions are `g.<id> >= <n>` joined by `&&`: no arithmetic, no `Math.*`, no expression-valued costs, barely any alternation, despite the engine supporting all of it. Lowbridge should expect the same convergence and price its grammar accordingly — every operator offered is a maintenance cost whether or not content uses it.
5. **`g.hp>=1` as a no-op gate.** When content writes a `require` that is always true — 23 times in the fork — the schema is asking for something it should not. Lowbridge makes `require` optional; keep it that way, and resist any pressure to make it mandatory "for uniformity".
6. **Mini-languages beget mini-languages.** `scena`'s `check: "money,600"` is a bespoke CSV condition sitting next to a perfectly good expression parser, on a single record. If Lowbridge ever adds dialogue, the condition must be an `Expression` run through the same parser as everything else.

One smaller note: the fork's 32 resource groups are a mess of translated Chinese, un-renamed Arcanum leftovers, an empty string and a case typo, with half the resources in one bucket. Lowbridge's 15 groups are currently tidy, but `group` is free text in `validate.ts`; a closed list would keep it that way for free.

**Non-goals.** The fork's distinctive systems — a 500×300 tile map in two 150,000-element arrays, a thread-scheduled factory sim, random-roll conquest, 77 achievements, cloud save — are out of scope for the current slice (village to Foundation) and mostly out of scope for Lowbridge entirely. They are useful here only as proof that the record vocabulary stretches that far, and as a demonstration of what it costs when it does: 4,520 records, 184 field names, and a 6.6 MB bundle to interpret them.
